# Context Governance — מדריך למשתמש

> **מי צריך לקרוא את זה:** אתה — בעל הפרויקט / המפתח שעובד עם Claude Code.
> **מסמך מקביל לסוכנים:** `~/.claude/docs/GOVERNANCE-AGENT-GUIDE.md`
> **גרסה:** 1.0 (2026-04-12)

---

## מה זה ולמה זה קיים

Context Governance הוא מערכת ניהול מידע והקשר שפועלת **אוטומטית** בכל סשן של Claude Code. היא נועדה לפתור 5 בעיות שגורמות לרגרסיות, בלבול, ואיבוד עבודה:

**בעיה 1 — "מאיפה התחלנו?"**
בלי governance: כל סשן חדש שואל "מה עשינו בפעם האחרונה?" ומבזבז 10 דקות על re-discovery.
עם governance: ה-bootstrapper מציג briefing אוטומטי תוך 5 שניות.

**בעיה 2 — "מי דרס את מי?"**
בלי governance: שני סשנים מקבילים כותבים ל-PLAN.md ודורסים אחד את השני.
עם governance: file-locking + parallel-session-merge מגלים ומיישבים קונפליקטים.

**בעיה 3 — "סיימנו אבל שברנו משהו אחר"**
בלי governance: Claude אומר "done" בלי להריץ בדיקות.
עם governance: Verification Gate חוסם "done" בלי evidence חיצוני.

**בעיה 4 — "למה החלטנו ככה?"**
בלי governance: החלטות מתועדות רק בהיסטוריית שיחה שנמחקת ב-compact.
עם governance: MEMORY.md שומר החלטות עמידות, lessons learned, ו-pitfalls.

**בעיה 5 — "איפה הקובץ הנכון?"**
בלי governance: מידע מפוזר ב-10 קבצים שחלקם סותרים.
עם governance: CONTEXT-MANIFEST.md הוא אינדקס-על שאומר מה authoritative, מה stale, ומה archived.

## מה נכנס לתוקף אוטומטית

ברגע שהמערכת מותקנת, הדברים הבאים קורים **בלי שתבקש**:

**בתחילת כל שיחה:**
- Claude קורא את קבצי ההקשר הקריטיים
- מציג briefing קצר: "מצב נוכחי / פעולה הבאה / סיכונים"
- אתה רואה ~3-5 שורות בתחילת התגובה הראשונה

**לפני כל עריכת קוד:**
- נבנית מפת השפעה (impact map) — אילו קבצים מושפעים
- אם הסיכון גבוה (קובץ קריטי) — Claude עוצר ושואל אישור
- אם הסיכון נמוך — עובר שקוף

**אחרי כל milestone:**
- PLAN.md מתעדכן ברקע
- MEMORY.md מקבל רשומה אם הייתה החלטה חשובה
- אתה לא צריך לעשות כלום

**בסוף כל שיחה:**
- HANDOFF.md נכתב אוטומטית
- הסשן הבא יקרא אותו ויידע מאיפה להמשיך

## מה עדיין דורש ממך פעולה ידנית

- **`/full-finish`** — release pipeline (git push, GitHub release). תמיד ידני.
- **`/context-governance full`** — ביקורת עומק. תמיד ידנית (פרט ל-cron שבועי).
- **סתירה בין קבצים** — כבר לא דורשת אותך. Claude מכריע לפי ראיה, תאריך ודירוג, רושם מה הוחלף ולמה, וממשיך. הוא עוצר ושואל רק כשהסתירה נוגעת למחיקה, לפריסה, להגדרות חיות או לסודות.
- **פעולות git הרסניות** — push --force, reset --hard. תמיד דורשות אישור, ו-`deny-git-bypass.sh` חוסם אותן.
- **push בסגירת סשן** — כבר לא דורש אותך. בסוף סשן Claude עושה commit לקבצים שלו ו-push לענף הנוכחי, אבל רק בריפו פרטי ב-GitHub (או בתיקייה מקומית) שאין בו אף קובץ מהרשימה של קבצי CI וכלי העלאה שהסקריפט מכיר. הרשימה ארוכה, אבל היא לא ערובה: בכל ריפו שדחיפה אליו יכולה להעלות משהו לפרודקשן, כתוב `close_push: off`. בכל מקרה אחר הוא לא דוחף, ורושם למה: ריפו ציבורי, ריפו של הארגון (INTERNAL), ריפו בשרת שאינו GitHub או בנתיב רשת (`\\server`), ריפו שיש בו CI כלשהו או קובץ כמו `vercel.json`, או ריפו שכתוב בו `close_push: off` בראש קובץ ה-CONTEXT-MANIFEST (בחלק שבין שורות ה-`---`). כדי שידחוף גם ריפו כזה, כתוב `close_push: on` ודחוף את השורה הזו בעצמך פעם אחת. שורה ש-Claude כתב בעצמו לא נחשבת. אם חיברת ריפו ל-Vercel או ל-Netlify רק דרך לוח הבקרה שלהם, בלי שום קובץ בריפו, Claude לא יכול לדעת את זה, אז כתוב שם `close_push: off`.

## הגנה מפני drift של סשנים מקבילים (2026-04-17)

אם אתה מריץ יותר מסשן Claude אחד במקביל על אותו פרויקט, יכולות להיווצר בעיות — סשן אחד כותב handoff, השני לא יודע ומשכתב אותו. כדי למנוע את זה נוסף הסקיל `/pre-close-check`.

**איך זה עובד:** לפני כל סגירת סשן (`/full-finish`), כתיבת handoff (`/live-state-orchestrator`), או סיום תכנית (`/plan-and-execute` שלב 3.3) — הסקיל מבצע 5 בדיקות אוטומטיות:
1. git log של השעה האחרונה (האם סשן אחר ביצע commits?)
2. mtime של קבצי handoff (מי נגע לאחרונה?)
3. version.json ↔ CLAUDE.md ↔ HANDOFF pointer (האם כולם מסכימים על הגרסה?)
4. ספירת handoff פעילים (חייב להיות בדיוק 1)
5. סינכרון CONTEXT-MANIFEST עם המצב בפועל

אם נמצאה פעילות מקבילית או drift, Claude פותר לבד ורושם את ההכרעה: ממזג את העבודה של הסשן השני, משאיר handoff אחד פעיל, ורושם שורה ב-Change Log. הוא לא עוצר ולא שואל, חוץ ממקרה אחד: כשהסתירה נוגעת למחיקה, להעלאה לפרודקשן, להגדרות חיות, לסודות או לנוסח של כלל. (מגרסה 2026-09-29. כדי להחזיר את העצירה: `GOV_CANONICAL_AUTORESOLVE=0`.)

**למה זה חשוב:** תקרית 2026-04-17 — סשן אחד כתב handoff של גרסת patch כפעיל, בזמן שסשן מקבילי שחרר את הגרסה שאחריה. בלי ה-check הזה, drift כזה לא מתגלה עד סשן חדש שמבחין בסתירה.

## היררכיית מקורות אמת

כשיש סתירה בין שני קבצים — מי מנצח?

8. **CLAUDE.md** — הנחיות כלליות

**ככל שהמספר קטן יותר — הוא authoritative יותר.**

## מחזור חיים של HANDOFF

HANDOFF הוא ה"פתק" שסשן אחד משאיר לסשן הבא.

```
[active] ←── סשן נוכחי קורא אותו
    │
    ▼
[consumed] ←── התוכן הועבר ל-PLAN.md / MEMORY.md
    │
    ▼
[archived] ←── לא רלוונטי יותר, שמור להיסטוריה
```

**כלל ברזל:** רק HANDOFF אחד יכול להיות `active` בכל רגע נתון. אם נמצאים שניים — Claude משאיר את החדש פעיל, מעתיק אליו את המשימות הפתוחות של הישן, ומסמן את הישן כמוחלף.

## סשן שממשיך לבד עד סוף המטרה (`/goal` + `/loop`)

לפעמים אתה לא נותן משימה אלא **מטרה**: "תסיים את X — כולל בדיקות, review, merge, deploy ואימות".
בשביל זה יש שתי הנחיות:

- `/goal` — מה התוצאה הסופית, מה בתוך ה-scope, ומתי זה נחשב גמור (Definition of Done).
- `/loop` — אל תחזיר לי שליטה עד שכל ה-Definition of Done מסומן.

**מה זה כן עושה:** Claude לא עוצר באמצע כדי לדווח התקדמות, לשאול "להמשיך?", או להגיש תוכנית במקום ביצוע.

**מה זה לא עושה:** `/loop` לא מבטל אף בלם בטיחות. Claude עדיין יעצור וישאל
כשחסרה ראיה חיצונית ל-Definition of Done, לפני פעולה הרסנית או בלתי-הפיכה, לפני release, ובצומת
שדורש אישור שלך. סתירה בין קבצי ההקשר כבר לא עוצרת את הלולאה — Claude מכריע, רושם וממשיך.

**עצירה כזאת היא בדרך כלל המתנה, לא סוף.** אתה עונה — והלולאה **ממשיכה מאותה נקודה**. אל תצפה שהסשן ייסגר בכל שאלת אישור. הסשן נסגר רק בשלושה מקרים: הקונטקסט נגמר, אתה עצרת, או שהחסם לא ניתן לפתרון בסשן הזה — אין ממי לקבל תשובה, או שהתשובה היא "לא עכשיו". רק אז נוצר פרומפט המשך, ורק אז העצירה היא **יציאה תקינה** מהלולאה ולא כישלון.

**כשנגמר הקונטקסט באמצע:** ב-91% Claude מפסיק להתחיל עבודה חדשה, מעדכן את קבצי הממשל, ומייצר
פרומפט המשך מוכן-להעתקה. הסשן הבא ממשיך מאותה נקודה.
**הגעה לגבול הקונטקסט לא אומרת שהמטרה הושגה.**

**איפה הפרומפט נשמר:** תמיד באותו מקום — `docs/context/NEXT-SESSION-PROMPT.md`. שם קבוע, בכל פרויקט.
הוא **נכתב מחדש מאפס בכל סגירה, או נמחק** — לעולם לא מתווסף לקיים. הסיבה: הקובץ נקרא כמו הוראה
עדכנית ואין בו שום סימן שהוא ישן, אז אם הוא נשאר מסשן קודם — הסשן הבא יפעל לפי מטרה שכבר הסתיימה.
`/context-governance` מתריע כשהוא ישן יותר מה-HANDOFF שלידו.

הספציפיקציה המלאה: `~/.claude/docs/NEXT-SESSION-HANDOVER.md`.

## Verification Gate — מה זה ולמה זה חוסם

לפני שClaude מכריז "סיימתי", הוא חייב להציג **ראיה חיצונית** שהעבודה עובדת:
- פלט בדיקה (test runner) עם PASS
- פלט build/lint עם exit code 0
- docker logs שמראים את ההתנהגות החדשה
- HTTP probe עם קוד תגובה צפוי
- screenshot של UI עובד

"בדקתי בעיניים ונראה לי בסדר" — **לא מתקבל.**

## Kill Switch — איך לכבות

אם משהו משתבש או חוסם אותך:

```bash
export GOVERNANCE_HOOKS=0
```

זה משבית את כל ה-hooks באופן מיידי. Claude חוזר להתנהגות רגילה. לא צריך לערוך אף קובץ. כדי להפעיל מחדש:

```bash
unset GOVERNANCE_HOOKS
```

## שאלות נפוצות

**"למה Claude שואל אישור לפני עריכה?"**
רק לפני עריכת קובץ קוד שמסומן HIGH risk. זה מונע רגרסיות שקטות. אפשר לאשר בלחיצה. קבצי ההקשר (PLAN, HANDOFF, MEMORY וכו') נכתבים בלי לשאול.

**"למה יש briefing בתחילת כל שיחה?"**
זה ה-bootstrapper שטוען הקשר. בלעדיו Claude לא יודע מה המצב הנוכחי ומתחיל מאפס.

**"למה Claude נחסם ואומר BOOTSTRAP GATE?"**
מגרסה 2.0.0, בפרויקט עם governance, Claude לא יכול לערוך קבצים, לשלוח הודעות, לעשות commit/push או להפעיל שירותים לפני שה-bootstrapper רץ בסשן. קריאה תמיד מותרת. Claude מריץ את ה-bootstrapper בעצמו וממשיך, בלי שתצטרך לעשות כלום. לכיבוי במקרה חירום: `"GOV_BOOTSTRAP_GATE": "0"` ב-`env` של `~/.claude/settings.json`, ואז להפעיל מחדש את Claude Code.

**"למה Claude עוצר ואומר Stop-Report?"**
מאז 2026-09-29 זה כמעט לא קורה. סתירה בין קבצי ההקשר Claude מכריע לבד: לפי ראיה, תאריך ודירוג. הוא רושם מה הוחלף ולמה, וממשיך. הוא עוצר ושואל רק כשהסתירה נוגעת למחיקה, לפריסה, להגדרות חיות או לסודות.

**"מה קורה אם אני רוצה לעבוד בלי governance?"**
`export GOVERNANCE_HOOKS=0`. או פשוט אל תריץ `/init-governance` — Claude יעבוד רגיל על פרויקטים שלא מאותחלים.

**"האם זה עובד על כל פרויקט?"**
כן. ה-skills גנריים. הם מזהים דינמית את המבנה של כל פרויקט דרך CONTEXT-MANIFEST.md. אין שום hardcoding.
