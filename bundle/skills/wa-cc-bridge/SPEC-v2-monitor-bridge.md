## 1. הבעיה (v1 הנוכחי)

- cron מעיר את **המודל** כל 60 שניות = תור מלא (כל הקונטקסט כ-INPUT/cache-read)
  גם כשאין הודעה — ~1,440 תורים ביום על כלום.
- זיהום הסשן ב-"✓" שקובר מידע חשוב; עיכוב תגובה עד דקה; פג אחרי 7 ימים.

## 2. עקרון v2 — למה אפס טוקנים במנוחה

טוקנים נצברים אך ורק בקריאת API למודל. ב-v2 מי שסורק את הלוג הוא **תהליך node
רגיל** שרץ על המחשב (כמו הגייטוואי עצמו) — קריאת קובץ מקומית, עלות CPU בלבד,
אפס קריאות API. המודל מופעל **רק** כשהסקריפט מזהה הודעה אמיתית ממקור מורשה,
ואז ה-INPUT היחיד הוא על אירוע אמיתי. אין polling ברמת המודל בכלל.

## 3. מקורות מורשים (allowlist)

קונפיג `~/.claude/.wa-bridge.json` (local-only, gitignored):

```json
{
  "sources": [
    { "jid": "<Ops-Group group JID>", "type": "group", "name": "Ops-Group" },
    { "jid": "<operator private chat JID>", "type": "dm", "name": "Operator One" }
  ]
}
```

- **כל הודעה ממקור מורשה = פנייה לקלוד** (בלי צורך ב-@cc). אופציית
  `requireKeyword: true` פר-מקור לקבוצות מעורבות.
- הודעות `[CC]` שלנו — מסוננות (מניעת לולאה).
- כל מקור שאינו ברשימה — נזרק בשקט. DM = רק המספר של המפעיל (אבטחה: אף גורם זר
  לא מפעיל את קלוד).
- fallback תאימות: השדות הקיימים `ccAgentGroup` / `phone`.

## 4. ארכיטקטורה — שתי שכבות

**מקור הנתונים (קיים):** הגייטוואי `<ADMIN_CONTAINER>` כותב כל הודעה נכנסת ל-
`~/.openclaw/admin-logs/admin-YYYYMMDD.log`.

**שכבה 1 — סשן פתוח (in-session Monitor):**
- בכל סשן CC אינטראקטיבי נחמש אוטומטית (SessionStart hook, בלי לשאול — הנחיה
  קבועה של המשתמש 2026-07-21) Monitor קבוע שמריץ את `wa-monitor.js`.
- הסקריפט עוקב אחרי הלוג (בדיקה מקומית כל שנייה, מעבר חצות אוטומטי, התחלה
  מסוף הלוג, טיפול בשורות חצויות) ופולט שורת JSON להודעה מורשית → קלוד מתעורר
  מיד ומטפל בתוך הסשן הפעיל, עם כל הקונטקסט שלו.
- **מנעול יחידני:** הסקריפט מחזיק `~/.claude/wa-monitor.lock` (PID + heartbeat).
  סשן מקביל שרואה מנעול טרי — לא מחמש (מונע טיפול כפול; gotcha הסשנים המקבילים).

**שכבה 2 — אין סשן פתוח (דמון 24/7):**
- דמון Windows (Scheduled Task ב-logon, restart-on-fail) מריץ את אותו
  `wa-monitor.js` במצב daemon.
- כשמגיעה הודעה: אם `wa-monitor.lock` טרי → סשן פעיל יטפל, הדמון שותק.
  אם אין מנעול → הדמון פותח סשן CC חדש (headless `claude -p`) עם ההודעה —
  והסשן החדש מריץ את **כל פרוטוקול פתיחת הסשן הרגיל** (governance lite,
  bootstrapper, ייבוא קונטקסט) לפני הטיפול, ועונה בוואטסאפ.
- המשכיות: הדמון שומר session-id ומשתמש ב-resume כדי ששיחת WA רציפה תישאר
  באותו הקשר.

## 5. מודל ה"מתווך" (הנחיית המשתמש — ללא שינוי בשיטת העבודה)

- ההתנהלות המלאה (תכנון, SPEC, אישורים, QA, governance, PR) — **בדיוק כמו
  בסשן CC רגיל, ללא שום שינוי.**
- תפקיד שכבת ה-WA בלבד: (א) לסכם את פלט הסשן ולשלוח בוואטסאפ; (ב) לשאול/להמתין
  להנחיות של המפעיל; (ג) להעביר את ההנחיות כמו-שהן לסשן כקלט משתמש רגיל.
- **אין לגשר זיכרון/לוג משלו.** בוטלה כתיבת ClaudeCodeSharedSession.md מתהליך
  הגשר. הזיכרון היחיד = מנגנוני הזיכרון הרגילים של הסשן עצמו.

## 6. כללי הודעות יוצאות (WA)

- קצר, ממוקד, תכליתי — מהות בלבד. בלי קטעי קוד, בלי לוגים, בלי markdown.
- עברית פשוטה; פריטים טכניים (נתיבים/פקודות) רק אם הכרחי ובשורה נפרדת (כללי BiDi/RTL).
- פרפיקס `[CC]` בכל הודעה (גם מסנן הלולאה תלוי בזה).
- שאלה למשתמש = הודעה קצרה עם אפשרויות ממוספרות; ממתינים לתשובה כאירוע הבא.
